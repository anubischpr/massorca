# Bot teams

Objective: add a Bot teams mode to MassOrca, desktop and mobile, for non-technical users, reusing what MassOrca already has.
Branch: claude/peaceful-solomon-017ef2 for phase 0; each later phase gets its own branch. Delivery: ask-on-risk. PRs target custom/integration.
Test runner: `pnpm test`, `pnpm tc`. Approved design: https://claude.ai/artifact/RciXSHfXaHRyWECoQrKRLx (version 17).

## Specs

- S1. Model: Company > Team > one Conference room > Tasks, each with its own thread, optionally grouped in Projects. Design canvas version 17 is the UI reference.
- S2. Phases, approved by the user: 0 foundations, 1 mode and teams, 2 Conference room and tasks, 3 projects and versions, 4 memory, hand-offs and integrations, 5 Workspaces option, 6 routines and webhooks.
- S3. Minimal scope: "tengamos MUCHO cuidado en NO hacer sobre ingeniería, la base de MassOrca ya tiene bastantes cosas que se pueden reutilizar, mantengamos esto a lo mínimo necesario."
- S4. Git: "agreguemos Git en el instalador pesará más, pero es necesario para que funcionen ciertas features."
- S5. Engram: "no nos olvidemos de Engram, lo íbamos a incorporar como nativo en el proyecto para el tema de memorias compartidas". Whether it also solves large binaries is an open question for phase 0 (user: "pensaría que podríamos utilizarlo aquí también a nuestra manera").
- S6. Access: "Bot teams en general manera modo full access por defecto, en settings se podría configurar si se quiere granularidad por team y qué modo tendría cada team". Reason: "para usuarios no técnicos es importante que no sientan fricción al realizar tareas."
- S7. Stopped reuses the status `done` with `interrupted`; no new status state. Assumption to verify: it survives a host restart.
- S8. Bot teams runs on the host selected in mobile; team data lives on that host. Sharing teams across hosts is out of this version.
- S9. Code is never copied from nightly-labs/openbot (PolyForm Noncommercial) or CopilotKit/openbot; ideas only.
- S10. Phase 2, create a task without starting it: a task can be saved as "Not started" in the Todo column, with no agent working on it, and starts only when the person says so. The task record must exist before its delegated child session is launched. Stopped stays separate: a task that started and was interrupted (S7).
- S11. Phase 2, bots read and create tasks from the conversation: a bot in a Conference room can create a task on request and list pending tasks from the real board, not from memory.
- S12. Phase 2, a Workspaces session that comes from a team shows that team's character beside it in its row, as in the user's reference from Codex.
- S13. Phase 2, automatic Team Lead: a mentioned bot leads the request. Otherwise one short query on the host compares the request with every bot's description; when several match, the bot with the fewest active tasks leads; when none clearly matches, the room asks the person. Bots do not each analyze the request. Jev is optional: "en el bot team, en realidad sin Jev también debería funcionar, utilizando el agente predeterminado que está elegido en settings. Sólo que demoraría un poco más y gastaría de la suscripción, que es más caro que utilizar Jev". The query uses Jev when it is on, otherwise the default agent chosen in Settings.
- S14. Phase 2, the lead owns the parent session and delegates to other bots as child sessions, each on its bot's engine, with no agent-choice card. The Conference room is a channel of the person's messages and short bot posts, not a merged transcript.
- S15. Phase 4, automatic memory: "empezamos por una memoria por team, esa es la memoria por defecto". "si la tarea está relacionada a un proyecto, como massorca, entonces va a la del proyecto, si es una tarea sin proyecto, va a la memoria del team". "si desde un team digo \"oye, recuérdale tal cosa a logística, para que en el futuro no se le olvide\", entonces la memoria debe estar guardad en el team origen y el destino". A project task reads both project and team memory (user: "Yes, read both") and saves to the project. Assumptions, not yet confirmed: a request about how the team works in general saves to the team; team memory is named from the team name; a relayed memory is two linked copies that record both teams, because "la memoria debería llevar el nombre de engram del team desde el que provino, por ejemplo \"de parte de marketing\", entonces si hay una actualización en las instrucciones de esa memoria específica, sabe a que team enviarle una copia de lo nuevo"; both copies share one Engram `topic_key`, so an update replaces rather than duplicates; an unknown target team is reported in the room.
- S16. Phase 2, bot editing, relayed by the parent session: "Hay una mejora, cuando se crea un Team, debería permitirme editar un bot creado para corregir cualquiera de sus atributos." Any attribute of a bot can be edited, in the create-team form and on existing teams, in the same form used to add one.

Ahorita no tengo cabeza para ello.
Bueno que hagan como tú mismo has dicho. Cuando surja una duda: elige la opción más conservadora y reversible, la anota como pregunta para ti y sigue." The suggested-team card reuses the existing Automatic agent choice card.

- Q17 (2026-11-02, version store, S4/L3). Versions are Git commits on hidden refs (`refs/massorca/versions/NNNNNN`), but in a private bare repository per team outside the folder (`<userData>/bot-team-versions/<teamId>.git`), not in the folder's own repository. Reason: the folder may have no Git, may be the person's repository, and a private store can never touch their branches, index, working tree or `.git`, nor show anything in `git status`. The cost: versions are not carried by a `git clone`/pull of the person's repository (moving a team to another host would need a copy of that directory). Alternative if you prefer hidden refs inside the person's repository when there is one. Limits, my choice because nothing states them: a file over 5 MiB is left out of the version (counted in `skipped`), a folder over 200 MiB or 20,000 files is not saved at all and the person is told; files the folder's own `.gitignore` ignores are not versioned or touched by a restore. It runs in the host process that owns the folder, using that host's Git (any command a Git 2.25 knows; no capability probe needed). Restoring first saves the current state as a version ("Before restoring"), then rewrites only files that differ and deletes files the chosen version did not have (the saved copy keeps them). Old versions are never deleted, so the store only grows.
