# Marketplace parity and audit (pv95)
Objective: every Marketplace category (tools, agents, skills, services) has the same page structure and functions, a CLI/RPC check reports per row whether its page opens and why not, and every item is audited on local, WSL and pv-vps.
Branch: claude/marketplace-pv84. Delivery: commits per unit, the orchestrator builds pv95. Test runner: `pnpm test <file>`.

## Specs
- S1 (L1 item 3): "Tools, agens, skills y services deben tener, en lo posible, la misma estructura y funcionalidades". Every catalog row in every category opens a page with: the host picker; install or connect on the picked host; uninstall, remove or disconnect; configuration (connection, and "quienes pueden utilizarlo"); the sections Banner, Connection, Advanced options, Danger Zone. Where a function cannot exist for an item, the page says why instead of omitting it silently.
- S2 (L1 item 3): "no tiene sentido que pueda elegir dónde instalar un agente y no poder hacerlo en una skill". Skills, including board skills (Browser use, Computer use, Linear, Orchestration, Price check) and built-in commands, get the host picker and install on the picked host where an install exists.
- S3 (L1 item 4): "acaso en el código no se puede ver cuando se puede acceder o no a una skill y cuándo se bloquea". An RPC check, reachable from the CLI, reports for every catalog row on a chosen host whether its page opens and why it is blocked when it isn't. It is computed by the same code the UI uses, and reports each page's structure (sections, picker, install, uninstall, config, access).
- S4 (L1 item 4): "Si no puedes hacer esa validación sobre el perfil y host del vps y local, entonces tu puerto de depuración está incompleto." The check works against this computer, a WSL distro, and a paired runtime host (pv-vps), on both the local preview and the pv-vps preview profile.
- S5 (L1 observation): "¿El sistema está funcionando a través de la nueva función nativa del marketplace o parece que funciona porque hay configuraciones externas que se realizaron?" Each row reports native or external, naming the external dependency (for example gh login, glab, ENGRAM_DATA_DIR, hand-edited agent config).
- S6 (L1 observation): Audit every catalog item on local, WSL and pv-vps; fix what fails; report the table: item, category, local, VPS, sections, uninstall, config, native or external.
- Assumption A1: "who can use it" means, per category: services and apps use the access policy (agents and bot teams); skills use the per-agent switches plus bot teams; agents use "Use this agent"/default; tools use the access policy where the tool is an MCP app, and otherwise state that every agent on the host can run it.

- S7 (L2 item 1): "Revisa que no sólo sean accesibles, sino que sus secciones y configuraciones estén completas y funcionando desde el marketplace." Every installed or connected app or service page shows its complete settings, including GitHub multi-account management (sign in more accounts, set the main account, remove each account) and any other setting lost when Integrations moved to the Marketplace in 47727b478c0.
- S8 (L2 item 2): "Los agentes aparecen, pero no se pueden instalar o desinstalar desde Marketplace". Agents install and uninstall from their Marketplace page on the picked host; existing installs are migrated or reinstalled on the previews first, never in production.
- S9 (L2 item 3): "Desde MassOrca deberían gestionarse todas las instalaciones o desinstalaciones de las aplicaciones del marketplace." Every Marketplace item has a working install and uninstall action.
- S10 (orchestrator): each action has an `orca` CLI equivalent.
